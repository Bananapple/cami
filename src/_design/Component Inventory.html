How to hand this off

In your repo (or a fresh project) open Claude Code and point it at three things, in this order:

  1. This document — Component Inventory.html. Read end-to-end. Sections A & A.5 are non-negotiable; B–F are the implementation contract.
  2. The token file — redesign-tokens.css. Drop into the project as the source of truth for color, type, spacing, radius, motion. All component CSS references token names only.
  3. The screen prototypes — Redesign.html and the JSX in screens/. These are the visual reference. They use inline styles and prop-based composition; treat them as the spec for what each screen looks like, not as production code to copy verbatim.

Suggested first prompt: "Read Component Inventory.html section A.5 first and tell me which backend dependencies I need to confirm with the team before you start. Then propose a build sequence based on section F's checklist. Don't write code yet."

This forces Claude Code to surface the schema/API gaps before generating frontend code that assumes data that doesn't exist.

A · Data flagsThings to fix in the data layer, not the UI

Two things that surfaced during design that are not pure visual concerns — they affect schema or data-derived labels.

DATA-1 · Class label is level, not type

The category chip on Schedule rows currently shows discipline (Pilates / Yoga). In a manager view that's not operationally useful — operators need to know level (Beginner / Open / All levels) to plan substitutions, capacity, and pricing. Discipline is implicit from the class title.

Schema: keep the category field on class_template, but the value rendered in <CategoryChip> on Schedule and ClassDrawer should be level. Discipline can stay as a separate field, surfaced only in filters and reporting.

Mockups using "Pilates/Yoga": Schedule.jsx, ClassDrawer.jsx — replace with "Beginner", "Open", "All levels" before merging.

DATA-3 · Booking-state codes leak to UI as raw strings

Today's check-in screen surfaces booking states like payment_failed and cancelled as raw enum codes. Render rule: all booking states pass through a label map and render via <StateBadge> with the proper tone — payment_failed → warn "Payment failed", cancelled → neutral "Cancelled", no_show → bad "No-show", checked_in → good "Checked in". Never render the enum code itself. The map lives next to the StateBadge component so it's the only place these strings exist.

DATA-2 · Plan label vs membership state are not the same axis

On the Clients list, the trailing state badge shows plan name ("All Inclusive", "10-Clip · 3 left") with a state tone. That's two axes collapsed into one. Plan is a category (clip card / subscription / drop-in / no plan); plan health is the state (active / low credits / lapsed / inactive).

Render rule: the trailing badge on a client row is plan health. The plan name belongs on the meta-line under the client's name, alongside last-visit date.

A.5 · Backend dependenciesThings the design assumes that may not yet exist

The redesign surfaces a few pieces of state the current backend may not track. Each item below is small in isolation — most are a column or a derived counter — but they need to be agreed on before frontend work starts. Stoplight key: 🟢 already in the data model · 🟡 likely derivable / cheap addition · 🔴 needs a new pipeline or integration.

Member & instructor states

enum expansion
  • 🟡 Member states rendered: Active · New · Lapsed · No plan. The Clients screen filters by these. active and no_plan are derivable; new = first booking within last 30 days; lapsed = last visit > 60 days.
  • 🟡 Member "On leave" — explicitly paused membership, distinct from lapsed. New enum value on member.status: on_leave. Operators set this manually; billing pauses; member doesn't appear in lapsed reporting.
  • 🟡 Instructor "On leave" — same idea on instructor.status. Excludes them from substitute-picker dropdown but keeps history visible.
  • 🟢 Plan health — derivable from existing fields: active if subscription current, low_credits if clip card ≤ 3 left, expiring if subscription cancels in < 14d, lapsed if expired. No schema change.

Booking lifecycle states

attendance + refund tracking
  • 🟡 Booking states rendered in Recent activity: Booked · Attended · No-show · Cancelled · Refunded. Need a single booking.status enum capturing all five. attended requires the instructor (or system) to mark check-in.
  • 🟡 Class fill rate "Past" mode needs actual attendance, not bookings. If no-show data isn't captured, the Past tab effectively shows booking rate, not fill rate. Worth being explicit about which one operators want.
  • 🟡 "First visit" flag on a booking — derivable as a count query but a denormalized boolean on the booking row makes the Class drawer's "Drop-in · first visit" meta-line cheap.

Waitlist with offer state

timestamped lifecycle
  • 🟡 ClassDrawer waitlist tab shows entries like "Offered 11m ago" and "In line · #2". Requires the waitlist row to track:
    • position (queue order)
    • status: waiting · offered · accepted · expired · declined
    • offered_at (timestamp)
  • 🟡 Unmet demand metric on Home — count of waitlisted members whose offer expired or who never got an offer before the class started. Derivable once the above states exist.

Traffic & conversion attribution

analytics integration
  • 🔴 Traffic sources by day — the Home Traffic card stacks visits per source (Google · Instagram · Direct · Facebook · TikTok). Requires a web-analytics integration (GA4, Plausible, Fathom) feeding daily counts per source or a UTM-tagged session tracker on the public site. This is the only 🔴 in the deck — it's the largest piece of new infra implied.
  • 🔴 Per-source conversion rate — visits-to-bookings attributed by first-touch source. Requires the booking event to carry a source attribution at signup, which means the signup form has to read the visitor's session source.
  • 🟡 Booking trend cash-in — already implied by existing booking + payment tables. Just needs an aggregation per period bucket.

Member activity feed & stats

denormalized counters welcome
  • 🟢 Recent activity on MemberDrawer — derivable from bookings + payments. No schema change; just an ordered query.
  • 🟡 Stats grid (visits this month · YTD · total spent · avg per week) — all derivable, but for any member with hundreds of bookings, denormalized counters on the member row make the drawer open in < 50ms instead of running 4 aggregations.

Class capacity & level

already covered, just verify
  • 🟢 Capacity on each class instance — assumed present. The Schedule row's "8/12" trail and ClassDrawer's "x/y booked" both depend on it.
  • 🟡 Level on class template (DATA-1) — see the data flag above.

BACKEND-7 · Class-type schedule cutover

prospective-only schedule changes
  • 🟡 Cutover date on schedule rules. When an operator edits a class type's recurring schedule, the new schedule applies from a chosen date forward. Existing future class_instances generated under the old schedule survive unchanged. Schema: schedule_rule.effective_from + effective_to (or a schedule_rule_versions table) so the materializer can pick the right rule per date.
  • 🟡 Materializer behavior: when generating instances for a date, look up the rule version active on that date. Existing instances are immutable once materialized; only un-materialized future dates pick up the new rule.
  • 🟢 Existing bookings stay attached to their original class_instance. No cascade. The cutover affects what gets created, not what already exists.
  • Exceptions table (schedule_exceptions) is already wired up per the schema review: cancel and reschedule kinds are read by the materializer. UI ships these two kinds for MVP; sub_instructor and relocate stay schema-only until follow-up.
  • UI surface: cutover-date callout under the schedule grid in ClassTypeDrawer. Default = next occurrence of the earliest day in the new schedule.

C · PrimitivesEleven components, contracts

Each card below is a one-component spec: props, variants, where it's used, and what it must not do.

01 · Button

<Button variant size />
variant"primary" | "secondary" | "ghost" | "danger" — default "secondary"
size"md" | "sm" — md = 32px, sm = 26px
iconOptional leading icon node, 14px
loadingReplaces children with spinner; preserves width
asChildFor wrapping <a> — keeps button styling

Rules

  • Primary on a single surface — never two on one action bar. Danger outlined; filled red is reserved for AlertDialog confirm.
  • Inputs share the 32px height so form rows align cleanly.

02 · Badge — three primitives

<StateBadge> <CategoryChip> <Count>

StateBadge — colored capsule with leading dot

tone"good" | "warn" | "bad" | "info" | "neutral"
childrenTitle-cased label rendered at runtime, never raw enum

CategoryChip — soft-fill capsule, color-coded by semantic type

childrenUPPERCASE, monospace. No border — background fill only.
variant"default" | "plan" | "frequency" | "time" | "level" — controls fill color
planInfo blue (--info-soft / --info) — Subscription, Clip card, Drop-in, product types
frequencyGood teal (--good-soft / --good) — Casual, Regular, Devotee
timeWarn amber (--warn-soft / --warn) — Morning, Midday, Evening
levelNeutral (--surface-2 / --ink-muted) — Beginner, Open, All levels
defaultNeutral — unclassified labels

Count — bare tabular numeral, NOT a pill

valuenumber or "x / y" string
labelOptional unit string ("credits", "booked")
tone"default" | "warn" | "danger" — applied to the number only, when the number itself is the alert

Rules

  • Pill shape (full border-radius) is reserved for StateBadge. CategoryChip uses --r-input (slightly rounded rectangle). Never wrap a count in either.
  • Always pass a variant. The correct variant is determined by what dimension the chip encodes — plan type, engagement frequency, time preference, or class level. Never use default for data that fits a named category.
  • On mobile, chips are hidden. Wrap chips in <span className="sm-hide-mobile"> on list rows — the drawer shows the full detail. Similarly, "last visit" meta text is hidden on mobile to keep the row clean.
  • Sits inline next to the row title — never in the trailing edge column where StateBadges live.
  • Marketing tags ("Most Popular", "Best Value") do not exist on /manage.
  • Active/Inactive on products is read-only on the row — toggling lives in the OverflowMenu (Spec 06).

06 · OverflowMenu

Group ordering

  • Group 1 — edit / duplicate / share

08 · Shell & NavRail

<Shell active> · <NavRail> · <PageHeader>

NavRail

  • 220px wide on laptop. --surface-2 background, 1px right border.
  • Fixed to viewport — never scrolls. The rail is position: fixed (or sticky-equivalent) with height: 100vh. The page content scrolls independently of the rail. Studio brand stays at the top, profile + sign-out stay at the bottom, regardless of how long the page is.
  • 5 fixed destinations: Home / Today / Schedule / Clients / Studio. Studio name doubles as wordmark — replaces the old "Studio Manager" top bar.
  • Active item: --surface fill on a --surface-2 rail with 1px line ring. Action color reserved for the icon accent only.
  • ⌘K search anchored bottom of rail. Profile + sign-out anchored to rail bottom — not page header.
  • Mobile (<640px): rail collapses entirely behind a burger; full viewport given to the page. Same item list when expanded.

Page scroll model

  • Page content area scrolls; rail doesn't. The Shell is a 2-column flex: rail left (fixed), content right (scrolls). Page-level overflow: auto lives on the content column, not on body or html.
  • PageHeader is not sticky. It scrolls with the content. (If a future screen needs a sticky header, that's an opt-in prop on PageHeader, not the default.)
  • Section eyebrows in long lists (e.g. Schedule day-groups, Studio sections) are not sticky on the page — they scroll naturally. They are sticky inside drawer bodies. See Drawer scroll below.

Drawer scroll model

  • Single scroll surface. Drawer header (title + tabs + headerMeta) is pinned at top. DrawerActions bar is pinned at bottom. Everything between scrolls as one unit. Lists inside the body do not have independent overflow.
  • Why: nested scroll regions (notes scroll + list scroll inside one drawer) confuse trackpad and keyboard navigation. One scroll surface = one mental model.
  • Section eyebrows are sticky inside the drawer body — when scrolling past Notes, the ATTENDING · 17 eyebrow + its trailing CTA stick to the top of the scroll area. Implementation: position: sticky; top: 0; on the section header, with a 1px --line-soft bottom border that appears when stuck (use a :has() trick or a sentinel + IntersectionObserver).
  • Tab switch resets scroll-to-top. Each tab is independent content; switching to Waitlist and back to Attending lands you at the top, not at your previous scroll position.
  • Nested drawers (member opens from inside class drawer) overlay with their own independent scroll. Closing the nested drawer restores the parent's scroll position.
  • Mobile (<640px): drawer becomes a bottom sheet. Same scroll model — header pinned top, actions pinned bottom, body scrolls.

PageHeader

  • Title 24px / 600. Sub-line 13px / muted. Single tabular count, never repeated below.
  • Trailing CTA = page-level primary action. One primary maximum.
  • Search and global actions belong in the rail, not the page header.

09 · Kpi

<Kpi label value unit? delta? trend? sub />
label11px uppercase eyebrow, ink-muted
value28px / 600 / tabular-nums. Number or signed string ("+4").
unitOptional small ink-soft suffix ("kr"), inline with value
deltaOptional percentage string ("+125%", "-40%")
trend"up" | "down" — colors the delta and prepends ▲/▼

Rules

  • Trend color is on the delta only, never the value. Up = good, down = bad — but only when "up" is actually good for that metric (bookings yes, churn no).
  • Tile is a bordered surface; never a fill-on-fill card. Hover = --surface-2.
  • Default grid is 2×2 on Home, but <Kpi> is reusable in any 2-up or 4-up section.

Home · /manage/home

period-toggled analytics dashboard
  • Greeting — "Home" + period label sub-line ("Week commencing 27 Apr"). Period toggle (Week / Month / Year) using <Segments> in the trailing slot.
  • KPI tiles — 2×2 grid of <Kpi> (new primitive). Each tile: eyebrow label, large tabular value with optional unit, optional delta with up/down trend, sub-line context.

  • Booking trend — bar chart card. Bars in --action; the last bar (in-progress period) at 70% opacity. Hovering any bar shows a dark tooltip with the bar's label, bookings count, and cash-in (kr). Non-hovered bars dim to 45% so the focused bar reads cleanly.

  • Exceptions sub-section — per-date overrides for a specific instance:
    • Eyebrow: EXCEPTIONS · N + trailing text-link + Add exception.
    • Helper line: "One-off changes to specific dates: cancel a class, or move it to a different time."
    • Each exception row: date column (110px, tabular-nums) · StateBadge (bad "Cancelled" / info "Rescheduled") · detail text · Edit text-link · × to remove.
    • MVP scope: support cancel and reschedule (time change) only. sub_instructor and relocate are in the schema but ship behind a follow-up — they need richer pickers.
    • Add-exception flow (sheet or popover, NOT a nested drawer): pick date from rule's future occurrences → choose kind → if reschedule, pick new time → optional reason → save. Materializer handles the rest.
  • Single scroll surface — entire drawer body is one scroll. Section eyebrow sticks. Form expansion inside a row scrolls naturally; long forms cause the parent body to grow, not a nested scroll region.
  • Drawer width — 720px. Wider than 520px because of the schedule grid. Mobile: full bottom sheet.
  • ⚠️ Cutover semantics (BACKEND-7) — saving a schedule change is prospective only. Existing future class_instances survive unchanged. The new schedule applies from the cutover date forward. Existing bookings stay attached to their original instance. The materializer must respect the cutover.
